# Engine throughput workload

Run `node packages/postgres/bench/engine-throughput.ts --url=postgres://... --mode=sustain --groups=1000 --mix=precise --rate=500 --seconds=30 --name=unique --out=/tmp/unique` against a disposable database. The driver drops `perf_items` and `perf_dim`. PostgreSQL must enable logical replication and `track_commit_timestamp`. Use a unique database and port. Pin Node with `taskset`; the separate writer is pinned to CPUs 4–7. Change that affinity in the driver on other machines.

This extends the direct Engine/PostgresAdapter approach in `latency.ts`. No HTTP, React, or browser is involved. All groups have distinct arguments and one subscriber on a single connection. Precise groups use an indexed bucket equality and three groups per bucket. Broad groups alternate unfiltered aggregate, join aggregate, and ordered top-row queries. The initial fixture has one row per bucket; half the writes insert and half update a seed row. Inserts grow the fixture during a trial. The writer uses eight independent connections, offers writes against wall time, and counts offers dropped when all connections are busy. Writes are external SQL; a final `engine.mutate` checks the mutation path but its throughput is not included.

`--mode=fanout --mix=broad --groups=1000 --readers=4 --pool=20 --runs=5` measures isolated writes after initial subscriptions finish. `--mode=tracker` measures analyze, uncached/cached readsOf and complete adapter.affects scans, five repetitions each. Profiling uses the same command prefixed with `node --cpu-prof --cpu-prof-dir=/tmp/unique`; profiled timings must not be mixed with ordinary trials.

Metrics: latency uses PostgreSQL commit timestamps and wall-clock delivery timestamps on the same host. Object results produce data messages, decoded at the direct connection callback. Only writes whose sequence appears in a delivered result contribute to latency; `observedWrites` exposes coalescing and the resulting latest-value sampling bias. This is not a per-commit delivery guarantee. Millisecond delivery clocks limit short latency resolution. Raw delivery and commit logs permit independent recomputation.

Each second records cumulative re-runs, received batches, RSS/heap, and current WAL minus the last committed batch position delivered to the engine. This measures received commit position, not replication-slot acknowledgement. A small nonzero WAL gap is normal. Node CPU is user plus system CPU divided by wall time (100% is one core); writer and database CPU are excluded. End RSS includes retained measurement records. `rerunsPerSecond` includes drain time; use successive sample differences for active-window throughput. `drainMs` includes a deliberate 100 ms quiet interval and must not be interpreted as pure backlog time.

Series identity includes source revision, Node/Postgres versions, affinity, host load, fixture, groups, rate, duration, readers and pool. There is no ruled performance budget. The desired knee is increasing WAL backlog or delivery delay across sustained windows, not merely high CPU. Short sweeps locate candidates; longer repeated trials must confirm them. Shared-host figures are exploratory measurements, not regression baselines. Correctness requires no error messages and completed initialization; the driver is not a replacement for the live-query fuzzer.

Keep raw logs/profiles outside git. Stop only the process IDs and cluster created for the series. Benchmark changes do not modify engine or adapter code.

For commit coverage, add `--coverage=on` and then run `python3 packages/postgres/bench/engine-coverage.py /tmp/unique/trial precise 1000`. Tracing adds `pg_current_snapshot()` to each query result. The offline tool finds the first delivered snapshot that includes each committed transaction for each affected group, reporting per-group latency and the time until all affected groups cover the commit. It includes coalesced writes. This mode changes the payload and adds measurement cost; compare traced runs only with traced runs. The offline implementation assumes a fresh cluster without transaction-ID wraparound and monotonically advancing snapshots for each group. It reports missing coverage explicitly.

`node packages/postgres/bench/engine-throughput-profile.ts capture.cpuprofile trial.jsonl` summarizes self and inclusive sampled time restricted to the measured window, excluding subscription initialization. Inclusive percentages overlap. `--writer-cpus=4-7` controls producer affinity. Peak RSS is the OS process high-water mark and includes initialization. The driver verifies final scalar results against fresh SQL after sustained trials; failures and overload errors must be retained with the results.
